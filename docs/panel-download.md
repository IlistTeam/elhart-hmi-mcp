# Загрузка проекта в ECP-10

Добавлены `fstudio_download_devices`, `fstudio_download_preflight`,
`fstudio_download_start`, `fstudio_download_status`. Работающий MCP и DLL
не обновляются автоматически. Python-файлы поставляются согласованным комплектом.

Поддерживается USB, единственная подключённая панель с VID0528/PIDA4A8,
проект ECP-10/F010/ID2050 и конкретная исследованная версия FSTools.exe 2.1.9.1.
Ethernet и выбор между несколькими панелями пока не поддерживаются.
Windows instance ID подтверждает присутствие USB-устройства, а не модель,
прошивку или серийный номер панели. Проверку совместимости продукта и CPU
выполняет штатный FSTools при загрузке. Неизвестные диалоги не подтверждаются.

## Порядок работы

1. Сохранить проект и успешно выполнить `fstudio_build_start`, дождаться
   `completed`, `compiler_success=true`, `cleanup_complete=true`.
   Сборка Elhart включает штатную упаковку через установленный pack.dll после
   компиляции. Она создаёт привязанный к fshmi.bin файл info.dat и карту обмена.
   Сырые результаты BuildAsync без packaging.json к загрузке не допускаются.
2. Получить `device_id` через `fstudio_download_devices` и сверить с целевой панелью.
3. Выполнить `fstudio_download_preflight(build_id, device_id)`.
   Проверяются хеши исходников, собранных файлов и установленного загрузчика.
   Изменение файлов после сборки требует новой сборки. Это относится и к базе
   `HMI/System/fs2.s3db`.
4. Вызвать `fstudio_download_start(build_id, device_id)` для проверки без передачи.
   По умолчанию `dry_run=true`. Опросить `fstudio_download_status(download_id)`
   до `dry_run_completed` и `cleanup_complete=true`.
5. Для согласованной записи вызвать start с теми же параметрами и
   **`dry_run=false`**. Этот вызов изменяет программу физической панели.
   После start опрашивать тот же download_id, не создавать повторную задачу.

При аппаратной приёмке заранее согласовать конкретную панель, проект, build_id
и SHA256 fshmi.bin. Проверить штатный журнал успеха, завершение процесса,
сохранение IP и поведение проекта на панели. Dry-run не подтверждает ни
передачу, ни запуск проекта, ни совместимость физической панели.

## Механизм

Из успешной изолированной сборки копируются проверенные исходники и Bin
в собственный каталог задачи. Пользовательский проект не передаётся загрузчику.
FSTools запускается на отдельном Windows desktop, без переключения пользовательского
рабочего стола. Штатный DownloadCommand редактора в итоге запускает
`-d "{project-directory}\\bin"`; нативный разбор дополнительно подтверждает
`-c en` (язык) и `-o 119` (OEM). Вызов не начинает передачу автоматически.

Адаптер проверяет идентификаторы, классы и ключевые подписи стандартных Win32
контролов. Он выбирает USB и Project, включает и считывает Keep current IP,
отключает force, удаление данных, замену RW/рецептов, синхронизацию времени
и автозакрытие. После проверки он отправляет WM_COMMAND контролу Download.
Мышь, координаты и захват экрана не используются.

Журнал ListBox и значение ProgressBar читаются из собственного процесса.
Только явное итоговое `Download Success!` даёт `hardware_success=true`.
Это подтверждение передачи файлов. Оно не подтверждает запуск программы на
экране: runtime_success и acceptance_passed остаются неизвестными до отдельной
проверки панели.
Процент 100, закрытие процесса и успех отдельного файла недостаточны.
Результат хранится в `artifacts/download-jobs/<download_id>/status.json`.
Прогресс является сырым значением штатного ProgressBar, не оценкой времени.

Один именованный mutex защищает подготовку/передачу/завершение между процессами.
В пределах установки незавершённая задача также запрещает повторный запуск.
Перед запуском и непосредственно перед передачей проверяются процессы FSTools.
Чужой или оставшийся после сбоя экземпляр запрещает передачу, включая экземпляры
другой установки MCP. Они не переиспользуются и не закрываются.
Ошибка записи служебного runner.json после создания работника не считается
ошибкой завершённой загрузки: клиент получает download_id и продолжает наблюдение.
Временная ошибка чтения status.json повторяется; длительная ошибка возвращается
как незавершённое наблюдение с тем же идентификатором.
После неизвестного исхода, ошибки передачи, диалога или ошибки завершения
задача требует ручного исследования и не повторяется автоматически.
Прерывание работника может оставить последний сохранённый статус без обновления;
это не подтверждение результата и требует проверки собственного PID и панели.

После команды передачи автоматического безопасного cancel нет: остановка
передачи может оставить панель в промежуточном состоянии. Через 600 секунд без
итогового сообщения результат считается неизвестным. Закрывается только
собственный загрузчик и его job; такие случаи требуют проверки панели.
Для восстановления специалист проверяет панель и архивирует запись задачи
вне download-jobs; инструмент автоматического сброса блокировки не предоставлен.

## Проверка 23 октября 2026 года

Исследована штатная цепочка DownloadCommand → IDownloadOperation → FSTools,
аргументы и Win32-контролы установленного загрузчика.
Отдельная копия проекта полностью собрана штатным компилятором:
build_id `988c5b3cc8d44cc2a758a6a0be67ac0d`.
Dry-run `a8c252d6eb344cf59364f5347168410d` прошёл с настоящим FSTools:
USB, сохранение IP, `transmission_started=false`, `cleanup_complete=true`.
Физическая передача в этой проверке не выполнялась.

Итоговая проверка через отдельный stdio MCP: 86 инструментов, успешные devices,
preflight, start(dry_run=true), status. Задача
`8ff052444f52461cbcdce5a2277ab352` завершена с cleanup_complete=true.
Проверены чтение непустого журнала и ProgressBar на явно синтетических значениях
в собственном FSTools (`tests/native_loader_contract.py`, без Download).
Все 58 регрессионных тестов прошли, включая 24 новых сценария и проверки
самостоятельной упаковки; дополнительно прошли 26 сценариев доступа к моделям
в существующем C#-наборе. Артефакты проверки остаются локально в artifacts.

Дополнительный аудит обработки запуска: 24 офлайн-сценария загрузки включают
ошибку записи PID после запуска, сбой создания процесса, статусы задач других
workspace, временную и постоянную ошибку чтения статуса, а также появление
другого FSTools перед передачей. После исправлений повторён настоящий dry-run:
`f130a02da4354884a95af4cb0558f894`, transmission_started=false,
cleanup_complete=true. Существование собственного FSTools и его исчезновение
после завершения также проверены через снимок процессов Windows.

На 23 октября аппаратная приёмка не была пройдена. Итог реальной проверки
26 октября приведён ниже. Проверка офлайн не заменяет испытание на панели.

## Исправление упаковки 26 октября 2026

Первая разрешённая физическая передача
`3135a4f9a3be42ca8cbd0b4007b0d040` получила Download Success, но пользователь
увидел на панели `error -05c-7: no Auth!`. Эта попытка не прошла аппаратную
приёмку. Был пропущен штатный этап упаковки между BuildAsync и FSTools.
Результат компиляции не содержал обязательного Bin/info.dat.

Теперь изолированная сборка выполняет тот же установленный managed-wrapper,
который штатная DownloadAsync вызывает перед запуском FSTools. Пароль упаковки
получается внутри библиотек производителя и не экспортируется. Версии библиотек
проверяются по SHA256; упаковка разрешена только внутри собственного снимка.
Проверяются сохранность исходников, наличие info.dat размером 1024 байта и
manifest всех выходных файлов. Квитанция packaging.json связывает эти файлы
с успешной упаковкой; изменение любого файла делает пакет непригодным.

Все 66 регрессионных тестов прошли после исправления. Отдельно штатный pack
проверен без панели, затем выполнены новая изолированная сборка
`d0a80fda0f334411ac2b4e28b54ef03a` и dry-run
`1912f4a9a3944024b7742cd2272a433c`. Исходники совпадают с ранее одобренной копией
побайтно. Результат повторной аппаратной проверки фиксируется отдельно.

Повторная передача `f6386596afaa4608b0615bc0a06f21ec` завершилась штатным
Download Success; журнал содержит передачу Bin/info.dat и карты обмена.
Загрузчик завершён. Пользователь подтвердил на физической ECP-10:
«Открылся проект HMI1.04, ошибки no Auth нет». Аппаратная проверка передачи и
запуска этого проекта пройдена. Keep current IP включён и считан обратно;
фактический IP независимо не прочитан, сетевой запрос к 192.168.1.200 ответа
не дал. Настройки сети и ПЛК не изменялись. Работающий MCP не перезапускался.
Эта проверка не подтверждает все функции проекта, Ethernet-загрузку или другие
модели/версии. Полное локальное свидетельство:
`artifacts/download-candidate/physical-acceptance-repair.json`.
