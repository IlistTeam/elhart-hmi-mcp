# План адаптации FStudio_MCP для ELHART HMI Soft

Дата: 14 октября 2026 года.

Статус: профиль Elhart, подключение плагина, нативное создание компонентов,
сохранение, повторное открытие и полная компиляция подтверждены на тестовом
экране. Оператор подтвердил его основные нажатия и переходы; демо SLM прошло
ручную проверку автоматического цикла, останова и ручного управления.
Ускорение времени исправлено: повторный цикл занимает около 56 реальных секунд.
Остаются остальные экраны/сценарии и визуальные доказательства. Навык и поставка
обновлены; цель плана ещё не достигнута.

Текущий результат: представительный экран с нативной кнопкой и числовыми
полями полностью собирается. Экспериментальный запуск FCS/FSGUI в офлайн-режиме
реализован. Захват Computer Use не восстановлен:
после разрешённого возобновления Computer Use захват окна завершился ошибками
`FrameArrived timed out` и `window capture timed out`. Пользователь подтвердил,
что тестовая страница отображалась; затем реальные нажатия проверены вручную
оператором в Manual46 и SlmTimer49. Реальные снимки ещё требуются.
Тот же отказ захвата подтверждён на Калькуляторе Windows после активации
свежего окна. После полного перезапуска Codex контроль повторён на новом
Калькуляторе: обе ошибки сохранились, хотя клавиатурное закрытие окна работает.
Отдельная диагностика Windows.Graphics.Capture остаётся незавершённой.
По указанию пользователя приёмку продолжаем совместно: оператор нажимает
кнопки и сообщает наблюдения, агент выполняет нативные операции через MCP.
Ручные наблюдения и предоставленные оператором снимки отмечаем отдельно
от автоматизированных проверок; запуск процессов сам по себе не является
подтверждением поведения симулятора.

## Цель

Создавать и изменять редактируемые нативные проекты ELHART HMI Soft через MCP:
экраны, текст, кнопки, индикаторы, числовые поля, изображения, действия,
адреса и демонстрационную логику. Проверять сохранение, повторное открытие,
полную сборку и поведение в симуляторе целевой версии.

Первый законченный результат — один представительный экран, созданный через
MCP, сохранённый, повторно открытый, полностью собранный и проверенный
в симуляторе Elhart. После этого расширить процесс на демо станции загрузки
порошка SLM для ECP-10, 1024×768, с обновлением каждые 100 мс.

## Архитектура

Сохранить разделение исходного проекта:

1. Python 3.11+ — stdio MCP, проверка параметров, пакетные запросы,
   управление задачами и изолированной сборкой.
2. C#/.NET Framework x86 — мост чтения DTO и плагин внутри Elhart,
   вызывающий штатные модели и операции на потоке редактора.
3. Named pipe — локальная связь Python с плагином текущего пользователя.
4. Проверки Elhart — системные настройки, состояния, геометрия,
   подписи, числовые ограничения, макросы и регрессионные сценарии.
5. Навык — требования, выбор инструментов, оформление и приёмка.

Основное создание компонентов выполнять через штатные фабрики и модели.
Прямое редактирование XML сохранить для подтверждённых специальных случаев
и ремонта, с сохранением QName, порядка DTO и семантики полей.
PowerShell оставить для сборки и проверок, которым нужен .NET Framework.

## Организация разработки

- Публичный форк FStudio_MCP: `IlistTeam/elhart-hmi-mcp`.
- Локальная рабочая папка: `C:\Codex\Elhart`.
- Git remote `origin` указывает на форк, `upstream` — на
  `TingRuazhang/FStudio_MCP`. Основная ветка сохраняет историю оригинала.
- План и необходимые документы перенесены в этот форк. Отдельный репозиторий
  планирования больше не используется. Локальная ветка `planning-bootstrap`
  сохраняет первоначальный коммит документов.
- Навык `elhart-hmi-projects` остаётся в своём существующем репозитории.
  После проверки адаптации обновить его интеграцию с MCP.
- Исходный FStudio_MCP получен через штатный GitHub fork. Все изменения Elhart
  оформлять отдельными коммитами поверх оригинальной истории.
- По возможности сохранить совместимые имена `fstudio_*` на первом этапе,
  чтобы уменьшить объём изменений; имя сервера и профиль обозначить как Elhart.
- Использовать Git с веткой `main` и отдельными ветками изменений.
  Не включать в коммиты пользовательские проекты, DLL производителя,
  журналы, локальные настройки и результаты сборки.
- Сохранить исходную MIT-лицензию и copyright при импорте кода.
  Библиотеки, шаблоны и другие ресурсы производителя брать из законно
  установленного Elhart; не включать их в публичную поставку.

| Место | Необходимая работа |
| --- | --- |
| Пути Flexem в server.py и скриптах | Профиль установки Elhart, единая конфигурация workspace и плагина |
| Template/HMI/zh | Проверить выбор OEM-шаблонов Custom/119, язык и профиль панели |
| Модель F010 | Сверить F010 / ID2050 / ECP-10 / 1024×768 / runtime a8 по установленному каталогу |
| BackgroundBuild.cs | Проверить контракты и зависимости сборщика; обращение к обфусцированному типу зависит от версии |
| Путь журнала Flexem/FStudio3 | Использовать фактический путь KIP/ELHART HMI Soft3 и журнал конкретной сборки |
| capabilities в server.py | Отделить исторические результаты FStudio от реально проверенных возможностей Elhart |
| Импорт изображения | Проверить необходимость и корректность обхода PictureOrigin на версии Elhart |
| Симулятор | Добавить отдельный проверяемый процесс запуска и визуальной/интерактивной приёмки |

Поле compiler_available=false в health моста задано в коде для этого
отдельного процесса; оно само по себе не доказывает отсутствие сборщика Elhart.
Поддержку компиляции проверять через плагин и полный цикл сборки.

## Регрессии, которые нужно сохранить

- QName в i:type и области объявления XML-префиксов.
- Порядок DataMember, особенно IsDisableWhenNotMatch в настройках кнопок.
- Наличие VisibilityInfo, условий, действий и GUID макросов после чтения DTO.
- Системные конфигурации, служебные окна и ссылки начального/главного окна.
- Полные bit-состояния и word-состояния с fallback.
- Полные числовые ограничения, длины строк и согласованность адресов.
- Квадратная геометрия кругов, пустые скрытые подписи и отступы текста.
- 10×100 мс, переключения экранов и повторные вызовы без ускорения процесса.
- Команды оператора не стираются публикацией состояния.

## Правила приёмки

XML parse → DTO load → модель → сборка макроса → полная сборка HMI →
симулятор → физическая панель — разные уровни подтверждения.

Для каждого результата записывать версию, проверенный сценарий, доказательства
и ограничения. Собственный рендер геометрии не выдавать за снимок Elhart.
Известная ошибка полной компиляции означает, что проект ещё неисправен.
Расширять покрытие 73 инструментов после завершения первого полного сценария.

## Ближайшая задача

Завершить совместную ручную приёмку SLM: настройки, калибровка, журнал,
оставшиеся блокировки и реальные снимки экранов. Дополнить крайние значения

соответствующими каждому изменению.

Тестовый сценарий обязан закрывать собственный редактор и его симулятор
в finally, после подтверждённого сохранения и закрытия проекта. Не запускать
следующий экземпляр при неизвестном исходе или живом предыдущем тесте.
