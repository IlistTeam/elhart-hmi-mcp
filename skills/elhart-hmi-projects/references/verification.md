# Проверка проекта

```text
python scripts/project_tool.py xml-check --project <папка>
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/validate_native.ps1 -ProjectRoot <папка> -InstallRoot <папка-Elhart>
```

Используй Windows PowerShell/.NET Framework:
C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe.
InstallRoot по умолчанию C:\Program Files (x86)\KIP\ELHART HMI Soft 3.x.
Общая проверка читает без перезаписи все окна, включая служебные, библиотеки,
макросы, индекс и системные настройки. Профиль сверь с установленным каталогом
отдельно. Отсутствующие основные каталоги — ошибка, а не
успех с нулём проверок. Сверяй число проверенных файлов.

`validate_native.ps1` также десериализует существующие системные конфигурации:
общие и расширенные настройки, языки, управление от ПЛК, события, сбор данных,
расписание, пользователей, почту, шрифты, мониторинг и видеовыход. Общие и
расширенные настройки обязательны. Проверяются ссылки начального/главного окна,
включённой заставки и положительные времена включённых режимов подсветки/заставки.
Старые проверки, читавшие в `HMI/System` только `ConnectInfo.cfg`, пропускали этот
уровень: положительный результат не подтверждал исправность общих настроек.
Проверка этих DTO и ссылок тоже не заменяет сборку системного сегмента HMI.

## Ошибка сборки общих настроек

В ELHART 3.0.15569.0 наблюдалась ошибка «Настройки системы → Общие настройки»
при сборке проекта, у которого XML, компоненты и макрос уже прошли отдельные
проверки. Журнал указал `Flexem.Studio.Build` / `SysSeg Build(...)`. Это место
сбоя, а не доказательство неправильного значения конкретного поля.

1. Сверь путь открытого проекта, версию редактора и время новой неудачной сборки.
   Прочитай соответствующий фрагмент штатного журнала; для этой установки это
   `%APPDATA%\KIP\ELHART HMI Soft3\Logs\Log.txt` (путь зависит от установки).
2. Выполни системные DTO-проверки и проверь ссылки из общих настроек. При переносе
   основы проверь GUID устройств во всех применимых системных адресах, а также
   служебные окна, требуемые выбранной панелью. Не заменяй GUID неиспользуемого
   адреса и не отключай функцию только потому, что сообщение указывает общий раздел.
3. В копии воспроизведи ошибку целевой версией сборщика. Меняй подтверждённую причину,
   сохраняя остальные настройки, и повтори тот же этап; затем выполни полную сборку.
   Изолированный IoC-контекст должен содержать необходимые сервисы: его
   `ServiceNotFoundException` или отсутствие каталога панели не доказывают дефект проекта.
4. После подтверждения исправления внеси его в генератор и, если дефект пришёл
   из основы, в соответствующий файл стартового архива. Добавь регрессионную
   проверку, которая падает на исходном дефекте и проходит после исправления.
   Пока причина не установлена, не записывай гипотезу как проверенное решение.

Проверки изменения системного валидатора:

```text
python scripts/test_system_validation.py
```

Тест работает на временной копии стартового проекта: исправный исходник должен
пройти, несуществующее начальное окно, нулевое время включённого режима и
неверное числовое поле общих настроек должны быть отклонены. Он не запускает GUI.

## Ошибка настроек управления кнопки

В ELHART 3.0.15569 наблюдалась «Ошибка настройки элемента Подготовка_40 в окне
B_1» и красная отметка вкладки «Настройки управления». Журнал содержал
NullReferenceException при чтении `GraphicsVisibilityModel.IsControlUserLevel`
из `ControlSettingsPropertyModel.VisibilityInfo`.

Подтверждённая причина: `IsDisableWhenNotMatch` (Order=2) был вставлен перед
`IsEnabled` и `VisibilityInfo` (без заданного Order). Штатная десериализация
успешно завершалась, но `VisibilityInfo` становился null, `IsEnabled` и
`IsTriggerMacroAfter` — false. В проекте пылесоса затронуты восемь кнопок;
сборка останавливалась на первой из них. Имя кнопки само по себе не доказывает
эту причину: проверь журнал и значения DTO конкретного проекта.

1. Сохрани копию исходных файлов и проверь порядок по контракту установленной
   DLL; подробности в [native-format.md](native-format.md#xml-префиксы-типов-имеют-область-действия).
2. Восстанови порядок в XML, сохранив условия, адреса разрешений, действия,
   GUID макросов и оформление. Не отключай блокировку для обхода ошибки.
   Исправь генератор и остальные компоненты с той же настройкой.
3. После повторного чтения проверь `VisibilityInfo`, `ConditionCollection`,
   флаги логики/блокировки, полярность и адрес разрешения, `IsEnabled`,
   `IsTriggerMacroBefore/After` и GUID макросов. Модель может создаться с null;
   успешный GraphicModelMapper ещё не подтверждает исправность управления.
4. Повтори полную сборку в редакторе и проверку симулятора. Изолированные
   обращения сборщика к VisibilityInfo проверяют только место прежнего сбоя;
   построение OperPrm требует сервисов активного проекта. Ошибку отсутствующего
   build-контекста не приписывай кнопке.

`validate_native.ps1` проверяет порядок ControlSettingsProperty по DataMember
установленной DLL, сохранение ключевых значений при чтении и наличие условий
для включённого управления. Регрессионный тест работает на временной копии
стартового проекта и не меняет проект пользователя:

```text
python scripts/test_control_validation.py
```

При правке файлов открытого проекта закрой старую копию без сохранения и открой
исправленную заново: сохранение старого состояния редактора может затереть ремонт.

## Проверки примера SLM

```text
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/slm_checks/run_checks.ps1 -ProjectRoot <папка>
```

Каждая проверка запускается отдельно: повторный Add-Type в одном процессе
конфликтует. Комплект привязан к 3.0.15569/SLM; обфусцированные методы особенно
зависят от версии. Для другого макета адаптируй ожидания; не восстанавливай
константы шаблона, чтобы замаскировать преднамеренное изменение дизайна.

| Проверка | Покрытие |
| --- | --- |
| loadcheck_slm_elhart -CheckWindows | GraphicModelMapper и полные модели в изолированном IoC |
| check_slm_editor_actions | Настоящие FetchAsChild действий/таймеров |
| check_slm_visual_states | Пара 0/1, visibility, состояния/PNG |
| check_slm_tags | Словный fallback через адаптер сборщика; индекс/миниатюры |
| check_slm_numeric_limits | 13 полей/52 границы через методы сборщика |
| check_slm_round_geometry | Размеры, пустые подписи кругов, квадратные PNG |
| check_slm_caption_positions | Корневые отступы подписей |
| check_slm_unit_spacing | Правое число/левая единица/зазор 8 px |
| check_slm_refresh_timers | Таймеры 100 мс, MM:SS.d |
| check_slm_ecp10_profile | ECP10, разрешение, границы объектов |
| check_slm_native_bitmap | PNG через штатный bitmap builder |

При изменении макроса:

```text
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/slm_checks/compile_slm_demo.ps1 -ProjectRoot <папка>
```

Команда создаёт временные бинарники и Validation в копии. Собирает Win32/ARM,
запускает тесты цикла, блокировок, затвора/воздуходувки, settings/calibration/CSV,
конкурирующих команд, 10×100 мс и дублей. Нужен согласованный demo_expanded.c.
Для обновляемого 100 мс примера проверяется также повторная загрузка DLL
на каждом вызове с общей памятью HMI; static-переменные между вызовами
не сохраняются. Этот тест воспроизводит дефект ускорения исходного примера.
Эти тесты не являются тестами произвольного оборудования.

## GUI и визуальная приёмка

Открой именно новую .fsprj: Elhart может автоматически открыть старую версию.
Полная компиляция → новый симулятор → каждый экран. Проверь рабочую
последовательность, до/во время/после нажатия, нули, предупреждение/аварию,
время при переходах, текст и пропорции. Сними реальные состояния.

XML parse → DTO load → модель/адаптер → сборка макроса → полная компиляция
HMI → симулятор → физическая панель: это разные уровни подтверждения.
Сообщай достигнутые уровни. Собственный рендер layout не доказывает отображение
Elhart; сборка ARM не подтверждает работу на физической панели.
